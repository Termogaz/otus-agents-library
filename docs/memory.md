## 2026-10-25 — Модуль 2, фаза 1 (закрытие пробелов): обходы .env и правок .claude/ (ветка `feat/module-2`)

**Сделано.** Закрыты обходы, которые воспроизвёл верификатор фазы 1. Токенизатор `shell.ts`
разбирает экранированную кавычку, clobber-перенаправление и `>&файл`, `$'…'`, группировку
`(…)`. Операнды вида `=`, `@`, `:` (`dd if=`, `curl -d @…`, `git show HEAD:…`) проверяются
через `isSecretOperand`. Конструкции, которые hook не моделирует (канал и heredoc в shell,
`eval`, `python -c`), отклоняются по fail-closed, если в команде виден секрет. Обёртки записи
(`FOO=1`, `env`, `nohup`, `xargs`, `sudo -u`) и писатели (`dd of=`, `curl -o`, `wget -O`,
`cp -t`) снимаются перед проверкой; `git add -f` понимает глобальные опции и широкий
pathspec; `reviewer` не читает секрет через `git diff`, `git show`, `git log`. Файл
`.envrc` добавлен в `.gitignore`. На каждый обход есть тест и парная легитимная команда;
`README` переведён на `.planning/` как место плана и прогресса.

**Решение.** Точечные правки токенизатора дополнены правилом fail-closed (немоделируемая
конструкция плюс упоминание секрета — отказ), чтобы не играть в whack-a-mole. Рекурсивный
`grep` по корню — `ask`, а не `deny`. Формулировка «6 закрыто, каждая проверена» из записи
ниже уточняется: «проверена» значит «есть проходящий тест», а не «обходов не существует».
Остаются ограничения эвристики: значение из переменной без буквального токена, скрипт
интерпретатора, собранный подстановкой, `git add -f` каталога с точкой в имени, писатели
`find -delete` и `git rm/checkout/restore/apply`. Они названы в `docs/security-checklist.md`
со ссылками на номера первого ревью (`01-REVIEW-before-gaps.md`), а не скрыты за статусом «закрыт».

**Дальше.** Повторная верификация фазы 1, затем фаза 2 — память и auto hooks. Открытые
находки первого ревью (`01-REVIEW-before-gaps.md`), уже названные в checklist: WR-05 (`isMain` без realpath —
hook молча не выполняется при запуске через symlink), WR-06 (ложные отказы, в том числе
добавленные fail-closed), WR-07 (Edit-правила `settings.json` только для путей от корня),
IN-03 (`allowed-tools` у `review-step` шире белого списка `reviewer`). IN-01 — дубль
импорта из `protect-files.js` в `tests/unit/protect-files.test.ts`: качество кода, не риск,
поэтому в checklist его нет.

**Ловушки.** Fail-closed может отклонить собственные команды агента, если они упоминают
секретный файл рядом с подстановкой, каналом, heredoc или `eval` — сообщения коммитов писать
обычным `-m`, а правки документов делать инструментами Edit и Write. `isSecretOperand`
делит операнд по `=`, `@`, `:`; расширенный хвост имени не трогает обрывки вида `.env*)`.
Критерий приёмки с `grep` по `eslint-disable|@ts-ignore|.skip(|.only(` совпадает с
литералами команд в страж-массиве `PLAN_COMMANDS`, а фильтр `-t "gitignore keeps envrc"`
выбирает 3 теста, два из них — элементы стража: это расхождение критерия с фактом, а не
дефект, записи стража не удалять.

книг, читателей и выдач, `listLoans({ bookId?, readerId? })`) и `StorageError` с кодом.
`src/server/json-file-repository.ts` реализует его на одном JSON-файле. Работа по TDD через
`write-tests`: 12 тестов в `tests/unit/json-file-repository.test.ts`. До реализации 10 красных на
проверках, 2 зелёных уже на заглушке (пусто, `undefined`). `npm run check` зелёный, всего 101 тест.

**Решение.** Формат файла — `{ version: 1, books, readers, loans }`, даты — ISO-строки. При чтении
файл проверяется zod-схемой, даты превращаются в `Date`. Коды отказов: `INVALID_STORAGE_FILE`
(не JSON или не по схеме) и `UNSUPPORTED_STORAGE_VERSION`. Версия проверяется до схемы, чтобы
файл новой версии не выдавался за битый. Файл читается при каждой операции, кэша нет. Операции
одного экземпляра идут по очереди, запись атомарная (tmp-файл, затем `rename`). Методы асинхронные,
чтобы потом подключить SQLite.

**Дальше.** 0.3c — API на zod + supertest, отказ домена → `409` с кодом. Путь к файлу —
`data/library.json` (в `.gitignore`), репозиторий передаётся в `createApp` параметром, чтобы в
тестах API подставлять временный файл. Rule-проверка, вторая половина: правка в `src/domain/`.

**Ловушки.** Rule-проверка, первая половина: при записи в `src/server/` и `tests/` rule `domain.md`
не подгрузился. `Array.prototype.with` не проходит `tsc`: `lib` в tsconfig ниже ES2023, поэтому
используется `map`, а tsconfig не трогали. Очередь сериализует только один экземпляр: два
процесса на одном файле могут потерять запись. Для одного сервера это допустимо, SQLite это снимет.

## 2026-10-18 — Шаг 0.3a: доменные правила выдачи (ветка `feat/domain`)

**Сделано.** `src/domain/types.ts` содержит `Book`, `Reader`, `Loan`, `LoanPolicy`, `LoanResult`.
`src/domain/loans.ts` содержит `checkoutBook`, `returnBook`, `isOverdue` и `DEFAULT_LOAN_POLICY`
(лимит 3, срок 14 дней). Работа по TDD через skill `write-tests`, агент вызвал его сам: 17 тестов
в `tests/unit/loans.test.ts`, сначала все красные (заглушки), потом зелёные. `npm run check` зелёный.

**Решение.** Отказы — `{ ok: false, code }`, коды: `NO_FREE_COPIES`, `LOAN_LIMIT_REACHED`,
`LOAN_ALREADY_RETURNED`. Если нарушены оба правила, отдаём `NO_FREE_COPIES`: это свойство книги,
а не читателя. `loanId` и `now` передаются параметром: домен не генерирует id и не берёт время.
Срок возврата — `issuedAt + loanDays × 24 ч`. Просрочка — строго позже `dueAt`, только у
невозвращённой книги. `checkoutBook` получает `loans` и сам отбрасывает возвращённые, поэтому
server может передать все выдачи книги и читателя.

**Дальше.** В новой сессии: 0.3b (репозиторий и JSON-файл) и 0.3c (API). Там же проверить rule
«в своей папке / в соседней»: сначала правка в `src/server/`, потом в `src/domain/`.

**Ловушки.** В этой сессии rule `domain.md` прочитан через `cat` до правок, поэтому проверка
загрузки rule здесь нечестная. Линтер-hook ошибок не нашёл, поэтому его срабатывание в 0.3a
не видно. Даты в домене — `Date`: при сохранении в JSON их надо превращать в ISO-строки и обратно.

## 2026-10-18 — Шаг 4: hooks (ветка `feat/hooks`)

**Сделано.** Три hook'а на TypeScript в `.claude/hooks/`, общий разбор shell — `lib/shell.ts`.
`protect-files` (PreToolUse `Edit|Write|Bash`) блокирует запись в `.env*`, `.git/`, `package-lock.json`,
включая `>`, `sed -i`, `tee`, `rm`, `mv`, `cp`. `format-and-lint` (PostToolUse `Edit|Write`) запускает
Prettier и ESLint, ошибки ESLint возвращает агенту кодом 2. `reviewer-readonly` подключён во frontmatter
`reviewer.md` и пропускает только белый список (`git status/diff/log/show`, просмотр веток, `npm run check`,
e2e, `ls/cat/head/tail/wc`). Логика — чистые функции, тесты в `tests/unit/` по TDD.
Проверено в сессии: `echo > .env` и `sed -i package-lock.json` заблокированы hook'ом; неотформатированный
`.ts` переформатирован, ошибка `no-unused-vars` пришла агенту.

**Решение.** Hooks на TS запускаются через `node_modules/.bin/tsx`: Node в WSL собран без поддержки
TypeScript (`ERR_NO_TYPESCRIPT`), а `tsx` уже есть в devDependencies. `tsconfig.json` расширен
(`include` += `.claude/hooks`), правила не ослаблены. Вход hook'а проверяется zod. При ошибке разбора
PreToolUse-hook'и отказывают (fail closed).

**Дальше.** Проверить hook `reviewer` в новой сессии, затем PR `feat/hooks`. После — шаг 0.3.

**Ловушки.** Hook во frontmatter `reviewer` в той же сессии, где его добавили, не сработал: `touch`
прошёл, хотя скрипт вручную отказывает (код 2). Вероятно, определения агентов читаются при старте
сессии — проверять в новой. Первая версия `protect-files` ложно сработала на тело heredoc (текст
`echo > .env` внутри `python3 - <<'EOF'`) — тела heredoc теперь вырезаются, есть тесты.
Без `npm ci` hooks не запустятся: ошибка запуска (не код 2) не блокирует вызов, защита молча пропадёт.
Bash-разбор — эвристика: `$VAR`, `$(...)`, `python -c` не раскрываются. Порядок: сначала `deny`
из permissions, потом hook — Write в `.env*` режет уже permissions.

## 2026-10-18 — Шаг 3: permissions (ветка `feat/permissions`)

**Сделано.** В `.claude/settings.json` — `permissions`: allow для проверок (`npm run check`,
`test`, `lint`, `typecheck`, `format`, `npx vitest run`, e2e) и read-only git; ask для `git push`,
`gh pr create/merge`, `npm install`; deny для `.env*` (Read, Edit, `cat`), `Edit(package-lock.json)`,
`rm -rf`, `git push --force`/`-f`, `git push origin main`, `npm publish`. Режим по умолчанию — `acceptEdits`.
Проверено в сессии: `cat .env`, `Read(.env)`, `git push --force` блокируются.

**Решение.** `acceptEdits`: правки файлов откатываются через git и проходят `/review-step`, а Bash
остаётся под allow / ask / deny. Read-only для `reviewer` permissions не решить — правила общие для
сессии и subagent'ов; переносим на шаг 4 (hook во frontmatter агента).

**Дальше.** Шаг 4 — hooks: линтер/форматтер после правки, блокировка защищённых файлов, read-only `reviewer`.

**Ловушки.** Bash-правила — префиксы строки команды, не песочница: `git push origin HEAD:main`,
`less .env` или `rm -r -f` их обходят. Это закрывает (частично) hook на шаге 4 и фиксируется в
`docs/about.md`. Правила для файлов — `Edit(...)` покрывает и Write; пути `./` — от корня проекта.
